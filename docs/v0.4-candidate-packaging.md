# Native candidate packaging (delivery step 4 / milestone 5a)

Candidate packaging is delivered for **Linux x86_64**, separate from the production
Python launcher. Full maturin wheels for Linux/macOS architectures and public
release publishing remain later work. The next launch step is deployment-host
validation and an observe-only trial; this development machine has no installed
Slack-connected daemon.

## Artifact and provenance

The final archive is in `dist/candidate/`. Its `build-manifest.json` records the
source fingerprint, locked dependency provenance, native Rust toolchain, required
glibc/shared libraries and hashes/modes/sizes for every payload file. The
standalone installer requires the expected archive SHA-256 and rejects symlinks,
traversal, duplicates, colliding paths and mismatched/missing/extra payloads before
creating the destination. An existing destination cannot be overwritten.

The candidate includes:

- `bin/fridica-candidate` and `bin/fridica-overseer-candidate`; no replacement of
  the production Python `fridica` command. The overseer binary currently exposes
  its offline planner, not an enabled campaign executor.
- All **25** embedded assets: template/contract/repository policy/Slack manifest,
  four preserved dashboard files, nine execution/diagnostic helpers, two worker
  result-format/schema files and six centralized SQL migrations.
- `share/README.md` with installation, configuration, fresh-state initialization,
  service start/stop/status/logs, upgrades and recovery instructions;
  `share/DEPLOYMENT.md` with build/config identity and milestone evidence fields.
- The verifier/installer, stopped-state SQLite snapshot/recovery tool, Cargo.lock
  and copies of the CLI/control, regression and recovery audit evidence.

This build requires Linux x86_64 with glibc **2.28+**, the shared libraries listed
in its manifest, and `/usr/bin/python3` for execution helpers. Packaged operator
scripts are supported on Python 3.11+. The installed binaries need no Python
Fridica package or source checkout. Real backend/SSH/confinement dependencies
are checked on each enabled deployment target. No other host was certified by
this local build.

Build from the matching checkout with cached Cargo.lock dependencies:

```sh
python scripts/package_candidate.py --verify-reproducible --smoke
```

Use `cargo fetch --locked` beforehand if dependencies are not cached. The recipe
builds release binaries with path remapping and fixed archive metadata, then
compares the entire archive against a second compilation in an empty target tree.
Reproducibility is scoped to the same source, native toolchain and host environment.
`reproducibility.json` and `candidate-smoke.json` bind results to the archive hash.
The smoke config fingerprint is synthetic and unique to its disposable directory;
it must never be substituted for the deployment config fingerprint.

## Guarded startup and recovery

`init-state --config` initializes v6 offline and refuses implicit legacy migration.
`service-print` emits a user systemd unit using the installed executable's absolute
path. The unit runs the daemon (`--observe-only` prints an observer unit);
generation neither installs nor enables it.
Paths are quoted and escaped for systemd without shell evaluation.

`start` runs the daemon and `start --observe-only` records intake only. (Until
2026-09-29 active startup also required `--active` and an owner deployment record
bound to build, executable hash, config and host; both were removed as friction for
single-owner use.)

Startup reruns readiness and backend auth/protocol doctor, then checks that the
config has not changed during the probes.

`share/state_snapshot.py` uses the same DB lock and SQLite Backup to capture
committed WAL state with matching config and hashes. Restoration writes a **new**
directory and never overwrites live state. The operator must explicitly switch the
stopped service to the restored pair after reviewing lost writes and external
effects. Migration rollback continues to refuse post-migration durable mutations.

## Verification

The isolated installed smoke runs from a disposable directory with a cleared
environment, synthetic tokens and scripted backend probes. A loopback proxy holds
Slack's CONNECT request without tunneling. It exercises both binaries, every asset,
init/configure/check-config, readiness/doctor, repeated fresh-state initialization,
`systemd-analyze verify`, real owner controls and exclusivity, SIGINT/SIGTERM drain,
active record/config/readiness/auth refusals, config changes during probes,
backup lock refusal, fresh snapshots, v5 dry-run/repeated migration/rollback and
explicit restoration after the durable-write rollback guard refuses. No real Slack
or model service is contacted.

CI has a separate native-candidate job after the Rust gate, runs corruption/snapshot
tests, independently rebuilds the archive, exercises installation, and uploads the
artifact plus both reports. Existing Python wheel CI remains in place.
