# v0.4 development status

This checkout contains a verified Python baseline, experimental Rust runtime and
**a native Linux x86_64 development candidate**. It is not a complete v0.4 release.
The production Python `fridica` entry point is preserved; the archive uses separate
`fridica-candidate` / `fridica-overseer-candidate` names. This development machine
has no installed Slack-connected daemon. Services default to observe-only.
Active startup now requires explicit opt-in and an owner deployment record bound
to build/config/host, then fresh readiness and doctor checks. Deployment validation
on the intended host remains outstanding; synthetic packaging smoke is not live
launch approval. See [candidate packaging](v0.4-candidate-packaging.md).

The [active launch plan](v0.4-active-launch-plan.md) separates checkout work from
deployment-host validation, includes a fresh-install path, and moves minimum
installation/service packaging ahead of the live trial. A live Slack installation
is not required to implement or test the candidate here.

Last audited against source and saved verification results: **2026-09-29**.
Rust library integration includes worker execution, attention, parent context,
Slack intake/delivery and scheduling, authenticated Unix controls, and owner-only
clean/restore with durable worker cleanup. The recovery/replay checkout gate is delivered. The full Rust run passed
**438 tests across 40 targets** for the packaging delivery; the final setup
wording check passed all **11 setup tests** with CI's two-thread setting. All 389 frozen Python
tests pass with the inherited unresponsive SSH-agent socket excluded. The cleanup
regression now checks actual permit release and process reaping; a separate
blocked-database test reproduces the old false-positive timeout. Shared active library composition is now implemented and
tested with simulated services. Step 1 startup readiness and explicit MCP source
inventory are delivered in the checkout. Owner-only live parent/workload
configuration editing, offline `init`/manual or detected `configure`, and general
`doctor` now have fixture coverage. General reply rendering, initial channel
context and invalid/unavailable parent settlement now have local coverage and
documented exceptions. Step 2's candidate CLI/control audit and regression
accounting are delivered; all 389 frozen Python regressions remain retained with
reviewed reasons. Native candidate packaging and guarded active CLI opt-in are delivered. Historical/deployment parity, actual-target isolation/backend conformance, the
credentialed campaign executor, verified overseer automation, scheduled reports,
MCP, cross-platform distribution and live rollout remain open.

The corrected implementation plan in the task supersedes the earlier RST design:
attachments use schema v4, scoped fetch v5, and Rust additions v6; campaign GitHub
operations must use existing owner `gh`/SSH authentication. No new token, GitHub
App, deploy key, or reviewer identity is introduced.
