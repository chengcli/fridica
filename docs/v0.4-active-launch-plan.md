# v0.4 active launch plan

Replanned on 2026-09-28 after confirming that this machine has no installed
Slack-connected Fridica daemon. This checkout is the development environment;
the eventual deployment host and its execution targets are separate inputs.
An existing daemon, live database, Slack credentials or historical corpus is
not required to continue implementation here.

This document sets the remaining implementation and launch sequence. The
[implementation status](v0.4-implementation-status.md) records what is actually
implemented and verified. It supersedes the rollout order in the older RST
proposal; the corrected v0.4 requirements remain in force. Replanning does not
complete any implementation or authorize installation, credential changes or
live posting on this machine.

## Initial launch scope

The first candidate enables ordinary attention and worker execution, including
owner controls, approvals, attachments and scoped fetch. Campaign execution,
the overseer, channel report posting and desktop MCP controls remain disabled.
Disabling desktop access does not remove the requirement to prevent workers
from accessing Fridica MCP/control credentials.

Keep existing Slack scopes, owner credentials and ordinary worker policies.
Only the owner may resume an explicitly owner-paused thread. Preserve separate
sticky placement, job permits and live-process limits. Slurm execution and
worker-process survival across daemon restarts remain out of scope.

## Milestones and exit criteria

### 1. Compose the active runtime in the checkout

Connect the real parent, worker supervisor/backend factory, approval broker,
instruction provider, scoped fetch, artifact IO, context services and attention
scheduler. Share composition with the CLI rather than building a separate test
daemon. Keep external boundaries injectable so tests can use simulated Slack,
scripted parent/backend executables, fake SSH and disposable state.

Deliver an end-to-end test of intake → parent decision → worker completion →
confirmed delivery → obligation closure. Exercise the same runtime wiring for
observe-only and owner-paused threads; they must not start models or workers.

**Checkout exit:** the composed path passes its integration tests, intake and
control effects are durable before acknowledgement, and pause/observe-only
gates hold. The active CLI refusal remains while development gates are open.

### 2. Integrate isolation admission and target checks

The shared active library runtime now runs the `doctor-isolation` probe before
each confined job's fetch/backend work, including warm-worker reuse. Runtime
startup and supervisor reload reject settings incompatible with the constructed
launcher/MCP options; isolation changes require rebuilding adapters. Launch-time
checks remain in place. Probe capacity survives cancellation until cleanup.
Active host startup now reruns the shared read-only readiness checks before
opening durable state. `start --check-ready` exposes the same report through the
CLI; success does not enable active CLI execution or certify real backends.
Unrestricted Codex now discovers supported file-layer identities on the target
and adds startup disable overrides; Claude retains strict empty MCP startup
settings. Owner-provisioned `settings_files` extend discovery beyond default
files, and `mcp_inventory_complete` records the owner's source/identity review
for each target. Unreviewed targets refuse readiness; missing or unsafe explicit
sources refuse discovery. Diagnostics remain bounded and private. Opaque/cloud
sources require registered aliases and actual-target review, not an automatic
claim of discovery completeness.

Test supported protocol envelopes, settings layouts, namespace failures,
inventory changes, cancellation and SSH disconnects with local fixtures. The
inventory is an owner assertion; discovery cannot certify absence of arbitrary
secret copies. Unrestricted workers retain the trusted-owner model.

**Checkout exit:** supported fixture configurations admit execution and unsafe
or unsupported configurations fail before backend initialization. Automated
preflight and lifecycle cleanup have regression coverage.

**Deployment exit, during milestone 5:** inventory each actual enabled target
and verify its OS, Python/bubblewrap, SSH, backend versions/protocols and existing
backend authentication. Record the tested versions and configurations. Local
fake-host tests do not count as this evidence.

### 3. Finish active behavior and recovery compatibility

Remote artifact collection and explicit owner-requested historical obligation
backfill now have checkout implementations and fixture tests. Parent context/note
edits, decisions and separate finished-discussion debriefs also have fixture
coverage, as do durable parent worker interrupt/stop requests. Owner-only live
parent/workload configuration edits now preserve comments, rebuild runtime
snapshots between passes, and reconcile interrupted file/SQLite updates. Complete
the remaining parent compatibility audit and CLI/control operations needed to run
the candidate. See [live configuration semantics](v0.4-live-configuration.md).
`init`, manual/detected `configure` and general `doctor` now have fixture coverage;
see [experimental setup](v0.4-setup.md). The remaining operational scope includes
the parent compatibility audit and candidate-required control operations. Dashboard serving, the `dashboard`
command and new UI work are deferred until the redesign direction is settled;
they are not step-2 or initial active-launch requirements. Preserve existing
dashboard behavior and regression checks during other changes.
Keep the regression map current; retain Python cases until equivalent coverage
exists. Backfill remains explicit; it never runs automatically on fresh installations or
upgrades, and unknown historical answer status is marked for owner review.

Exercise configuration changes during jobs, approval cancellation, session reuse,
retry-once execution, deferred intake and reservation reconciliation. Verify
hourly ceilings of 6 peer-triggered and 20 non-owner-triggered replies, streak
signal 3, visible mention dispositions and confirmed-delivery closure. Blocked
notices must not satisfy asks; new mentions must not resume owner-paused threads.

**Checkout exit:** compatibility cases have replacements or justified retention,
and concurrent restart/control/worker tests demonstrate no lost work, duplicated
effects, capacity leaks or owner-pause bypass.

### 4. Close deterministic replay and fault gates

Start complete boundary capture alongside milestone 1. Record parent responses
and errors, external context, worker completions, delivery outcomes and event
ordering, with injected clocks and identifiers. Extend the current synthetic
flows across the composed runtime and compare verdicts, inbox/outbox effects,
jobs and session transitions. Script new attention calls explicitly.

Use newly captured complete fixture tapes for exact supported parity. Historical
`action_json` rows cannot reconstruct missing responses or context. Relationship-
preserving redacted fixtures do not establish exact prose parity. Every parity
exception must identify its fixture, behavior and rationale.

Exercise duplicate intake, ambiguous delivery without automatic resend, EOF/exit
ordering, cancellation, remote disconnects, throttling/restart, migration crash
boundaries and configuration races. Diagnose the intermittent subprocess cleanup
timeout; a passing rerun alone is not evidence that the flake is fixed.

**Checkout exit:** full Rust regression, architecture, existing dashboard, replay and
migration checks pass with zero unexplained replay differences and no unresolved
required-check failures. Fresh installation, repeat upgrades, interruption
recovery and post-mutation rollback guards are covered using disposable data.

**Release evidence still outstanding:** obtain and redact the absent historical
corpora and evaluate their supported assertions. Their absence does not block
checkout implementation or synthetic capture, and must not be silently marked
complete when a development candidate is built.

### 5. Package locally, then validate on the deployment host

#### 5a. Produce a deployable candidate in the checkout

Move minimum installation and service packaging before the live trial. Produce
a versioned artifact for the selected deployment platform with required assets,
an experimental configuration example, fresh-state initialization, a service
definition and instructions for start, stop, status, logs, backup and recovery.
The artifact must not depend on running from this source checkout. Install and
exercise it in a clean disposable environment with simulated services.

Verify that clean installation does not require a Python daemon or old database.
Also rehearse upgrades/restoration against fixture databases and copied configs.
Keep the production Python package entry point until its replacement gates pass;
the candidate needs an explicit invocation and must not silently replace it.

**Checkout exit:** a reproducible artifact, clean-install smoke results and a
deployment checklist identify the exact build/config and passed milestones 1–4.
Only then replace the blanket active CLI refusal with explicit opt-in guarded by
the required checks; default installation/service configuration stays observe-only.
Full cross-platform wheels and public release publishing remain later work.

#### 5b. Install and validate on the intended deployment host

Obtain the host/platform, owner-managed Slack configuration and credentials,
enabled execution targets, backend authentication and complete private-file/MCP
inventories. These are deployment inputs, not reasons to install a daemon on the
development machine. Do not collect secrets in fixtures or documentation.

Choose the applicable state path:

- **Fresh installation:** initialize a new v6 database and private control paths.
  There is no production database to migrate and no prior Python environment to
  retain. Verify backup/restoration for the newly created state.
- **Existing installation upgrade:** stop the old daemon, back up database and
  configuration, rehearse migration/restoration on copies, and avoid simultaneous
  writers. Retain the old Python environment for two weeks. After durable v6
  mutations, recovery requires explicit backup restoration; do not automatically
  downgrade the database.

Run the actual-target checks from milestone 2. Start observe-only, validate Slack
identity/access, and inspect catch-up, duplicate intake, watermarks, obligations,
control responsiveness and logs. Require zero model calls, worker launches or
posts in this mode. Record the observed results against the installed build.

**Pre-active exit:** installation, target conformance, recovery rehearsal and
observe-only reconciliation pass, with no unresolved blockers. Scope the trial
to the channels and targets that passed these checks.

#### 5c. Run the controlled active trial

Enable active behavior explicitly only after the pre-active exit. Run the planned
week of live attention, recording obligation dispositions, throttling, deliveries,
worker failures, restart recovery and owner controls. Preserve stop controls and
investigate any discrepancy; material fixes require the affected gates to rerun.

**Trial exit:** no unresolved lost-work, duplicate-delivery, isolation or authority
failures, and every mention has a visible durable disposition. A week of live
attention happens after initial active enablement, not before it.

## Later v0.4 completion

The trusted owner-credential executor and verified overseer still require their
security/evidence gates and a three-PR trial with human merges. Scheduled reports,
retention/catch-up, campaign mirrors, opt-in posting, desktop MCP and dashboard
views remain unfinished. MCP read-only deployment precedes optional controls.
Dashboard serving, its CLI entry point and new views will be planned together
after the redesign decision, outside the initial active-launch gates. Existing
dashboard code remains available; this deferral does not require replacing it now.
Complete maturin dual-binary packaging, Linux x86_64/aarch64 and macOS x86_64/arm64
wheels, sdist and release/install verification before v0.4.0 publication.

These deferred features remain part of the original plan. No historical-corpus,
full-parity, human-merge or live-release gate is waived by the initial trial scope.

## Current delivery sequence

The five-item implementation sequence discussed after this replan groups the
milestones above as follows:

1. **Startup readiness — checkout delivered.** This completes the startup work
   from milestones 1–2: shared active host wiring, `start --check-ready`, local/SSH
   target checks, explicit extra MCP settings sources and owner coverage
   declarations. Fixture tests cover refusal before durable state or Slack I/O,
   confined executable visibility, bounded stop/cleanup, and active owner-control
   startup/shutdown behind a loopback proxy. No live daemon was installed.
2. **Behavior compatibility — in progress.** Remote artifact collection and
   explicit historical obligation backfill, parent memory/debriefs, durable worker
   controls, live parent/workload configuration edits, `init` and manual/detected
   `configure` and general `doctor` are implemented. Finish milestone 3's parent
   compatibility audit, remaining operational CLI/control work and
   regression accounting. Dashboard work is deferred pending its redesign.
3. **Recovery and replay.** Complete milestone 4, including diagnosis of the
   existing intermittent subprocess test failures.
4. **Candidate packaging.** Complete milestone 5a and its clean-install checks
   before enabling the explicit active CLI opt-in.
5. **Deployment validation and trial.** Complete milestones 5b–5c on the intended
   host, with real target inventories/backend conformance and observe-only first.

Step 1 is a development delivery, not permission to launch. Its report always
returns `active_launch_ready: false` and identifies the later gates. Source
coverage declarations are owner assertions, and target version/protocol/auth
checks remain deployment evidence. See the [implementation status](v0.4-implementation-status.md)
for verification and [worker configuration](worker-isolation.md) for usage.
