# Step 2 parent compatibility audit

This audit compares the Rust library runtime with the frozen Python parent,
thread policy and rendering implementation. It uses local fixtures; it does not
certify live backend conformance, complete replay parity or active-launch readiness.
Dashboard serving and redesign remain outside step 2.

| Area | Checkout evidence and remaining work |
| --- | --- |
| Parent CLI transport | `tests/parent.rs`: both tool-less stateless envelopes, model selection, bounded output/deadlines, cancellation, context snapshots and durable call records. Strict malformed-envelope/tool-attempt rejection is a documented exception. Actual CLI installations remain deployment evidence. |
| Participation and attention | Gate corpus plus actor/runtime tests cover triage, owner pauses, observe-only, blocked reopening, obligations and throttling. v0.4 deliberately replaces automatic loop pauses with signals. |

Repeat checks now inspect the most recent reply's delivery state and original
requester inside the actor transaction. The `actor_commit` replay record retains
that evidence and the repeat decision. This prevents a delivery completed while
the parent was running from being evaluated using stale state. Legacy outbox rows
without `trigger_event` use the original message inbox reference. No schema change
or historical obligation backfill is required.

An ambiguous send alone does **not** permit another identical answer on a routine
follow-up. This intentionally tightens the frozen Python rule. A new question,
explicit mention/repost request, different human requester or authenticated resume
is a new interaction and remains eligible under the normal attention gates. This
never resets, retries or resolves the earlier ambiguous outbox row.

The frozen repost matcher has narrow phrase and negation rules; these are preserved
for the captured supported cases. Fingerprints use Unicode case folding and Python
whitespace rules rather than lowercase-only comparison. The pure corpus is generated
with `PYTHONPATH=spec python scripts/capture_reply_policy.py`; it contains 34 repost
cases and 11 fingerprints, including negation, overlapping phrase matches and
Unicode. It is synthetic evidence, not historical message capture.

General reply formatting uses the configured Slack limit for the preview and
retains overflow in the details upload. Details-only replies receive a pointer;
blank replies are quiet and cannot answer obligations. Known bare participant IDs
are rendered outside code, links and existing mentions. Waiting replies address
the original requester. Answered obligations close only after both the linked
message and any required details upload are confirmed. Rejected or ambiguous
uploads leave the answer pending. The renderer corpus is generated with
`PYTHONPATH=spec python scripts/capture_reply_rendering.py`; all 72 synthetic cases
match frozen Python exactly. Rust separately rejects raw reply text or details
over 40,000 characters instead of Python's unbounded text/silent details truncation.

Channel context selects only roots strictly earlier than the current root and
orders them chronologically. The frozen budget counts text plus 80 characters per
message and always retains the newest message, even when that one message exceeds
the budget. It is a soft budget, not a 4,000-character hard truncation. A channel
message arriving during a decision cannot alter its repair snapshot.

After one unsuccessful repair, Rust deliberately rejects the entire action;
Python salvages valid portions. Jobs, controls, memory and obligation answers may
depend on each other, so applying a subset would make their effects unreliable.
The fixed blocked reply, status note, parent-call records, audit and inbox
settlement commit together. No proposed effect or answer disposition survives.
Ordinary parent unavailability produces the frozen blocked reply without a model
retry. Recording/context boundary failures instead retain failed-inbox recovery
and never acknowledge an unrecorded effect.

The latest failed decision durably holds automatic obligation-due work for owner
review. Due events remain pending with a 60-second deferral and cannot call the
model or post while held. Explicit new interactions and worker results may still
proceed under the normal gates; a successful decision/repair clears the hold.
Owner pauses, observe-only mode and reply ceilings remain enforced. A blocked
notice never satisfies an ask, and pending due work survives restart and resumes
after successful reopening.

Items 1–5 are delivered for step 2. The
[CLI/control audit](v0.4-cli-control-compatibility.md) accounts for candidate
commands and routes, and the [regression ledger](v0.4-regression-accounting.md)
records scoped evidence, deliberate differences and specific retention for every
frozen case. All production Python cases remain retained.
Recovery/replay fault diagnosis and packaging belong to subsequent delivery steps.
