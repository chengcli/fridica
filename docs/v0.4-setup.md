# Experimental Rust setup

The development Rust binary supports `init` and `configure`. These commands do
not install or launch a daemon, initialize a database, or establish active-launch
readiness. The production Python launcher remains unchanged. Dashboard work is
deferred pending redesign.

`fridica init` creates `~/.config/fridica/config.toml`, with `contract.md` and
`manifest.yaml` beside it. `--config PATH` selects another location. Existing
configuration is refused; existing companion assets are preserved. New files use
0600 permissions and newly created directories use 0700. Files are published
atomically with file/directory syncing, and configuration is published last. A
partially completed initialization can be retried while configuration is absent.
It does not create the template's workspace or state directory.

The Rust template includes attention ceilings of 6 peer-triggered and 20 total
non-owner-triggered replies per hour, with streak signal 3. It has no legacy
loop-pause fields. MCP inventory starts explicitly unreviewed. Complete the
workspace and isolation inventory settings yourself. GitHub API access uses the
owner's existing `gh` authentication; the manifest preserves the existing Slack
scopes. The `assets` command fingerprints the actual embedded Rust template.

`fridica configure` accepts `--owner-id`, `--workspace-id` and repeated
`--channel-id` options, together or separately. Channels are deduplicated in
input order. It validates those identities while allowing unfinished machine,
workspace or policy settings, and preserves TOML comments and unrelated fields.
It uses the same default path and `--config` override as `init`.

`fridica configure --detect` reads the configured `slack.user_token_env` variable
(default `SLACK_USER_TOKEN`) and uses that user token to read Slack identity and
joined public/private channels. Repeat `--channel-name NAME` for unattended
selection; a leading `#` is accepted. Without names, selection requires a terminal
and explicit comma-separated channel numbers. Empty input or EOF cancels without
changing the file. Detection cannot be combined with manual IDs.

Discovery rejects bot identities and ambiguous names, warns about missing read
scopes, and excludes unjoined/archived/direct-message conversations. It uses only
`auth.test` and `conversations.list`, without redirects or automatic retries.
Requests have a 15-second timeout and discovery has a 60-second overall deadline;
pagination, response sizes, IDs and channel counts are bounded. Errors use fixed
or allowlisted diagnostics, and credential echoes are redacted. No credentials
are written into configuration or a new database.

The configuration snapshot is taken before detection/selection, and the file must
still match before replacement. A private sibling edit-lock file coordinates
Fridica setup and live API writers; simultaneous edits are refused. API errors, invalid selection or a changed file
prevent publication. Configure validation/discovery errors exit with status 2.
These are offline setup edits: coordinate external file editing, and restart an
existing daemon to use changed Slack identities/scope. Live parent/workload edits
use the separately journaled [control API](v0.4-live-configuration.md).

After finishing setup, `fridica check-config --config PATH` validates the whole
file. `fridica start --check-ready --config PATH` performs read-only startup
preparation without invoking backends or reading token values. Active CLI startup
remains gated, and real Slack/backend/host validation belongs to the deployment
phase. Local fixture tests do not establish those live results.

`fridica doctor [--config PATH] [--json] [--timeout SECONDS]` checks the operating
system, configuration, owner contract/repository list, Slack token types and
previously recorded attachment scope. It checks the parent backend locally and
every configured worker backend on its target: workspace directories, required
help/protocol features, automatic-approval support when configured, sign-in, and
Linux bubblewrap/socat dependencies and user namespaces. Slurm is reported as
unsupported and skipped. Failed checks exit 1; warnings/skips alone exit 0.

Doctor runs backend help, authentication-status and Codex schema-generation
commands, never a model session. These commands use the owner's existing backend
installation and sign-in. A fixed embedded Python helper performs the short target
probes; `/usr/bin/python3` must be available. Subprocess output and schema reads
are bounded to 4 MiB, and output is replaced with fixed diagnostics. Slack and the
configured daemon GitHub-token variables are scrubbed locally and on SSH targets.
Schema generation uses a private temporary directory removed after the probe.
Doctor does not create or migrate a daemon database or call Slack. An existing
database is opened read-only for recorded scope metadata; this is not a current
Slack authorization check.

`--timeout` is a per-probe deadline of 1–120 seconds (default 30), with up to three
additional seconds for helper/SSH completion and bounded process cleanup. Targets
are checked sequentially. On a stop signal, the current bounded probe finishes
cleanup and later probes are skipped. SSH requires noninteractive authentication
and an already trusted host key, disables persistent connection reuse and host-key
updates, and does not enable agent forwarding. Diagnostics do not print raw
subprocess output, credentials or configured filesystem paths.

Doctor's backend diagnostics complement `start --check-ready`; run both. Reviewed
MCP inventories, settings checks and target confinement remain startup-readiness
checks. Doctor always reports `active_launch_ready: false`. It does not certify
live backend conformance, GitHub campaign credentials, or the remaining release
gates. The frozen Python doctor regressions remain retained pending full parity.
